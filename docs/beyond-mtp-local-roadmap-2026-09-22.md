# После MTP: что исследовать на Qwen3.5 локально

Дата проверки первоисточников: **22 сентября 2026**. Машина проекта: **M2 Pro, 16 GB unified memory**, target: **Qwen3.5-9B, MLX 4-bit**, один запрос. Это исследование и проект экспериментов: новые модели, training и длинные GPU-прогоны в рамках этой заметки не запускались. Предыдущий [широкий обзор](inference-acceleration-survey-2026.md) сохраняет сведения о kernels, KV compression и serving; здесь акцент на следующих локальных экспериментах.

**Мой порядок:** сначала n-gram/suffix draft без новой нейросети; затем измерить top-k coverage у уже скачанного DFlash; после этого выбирать между дешёвым selector и деревом кандидатов. Параллельная проверка шагов рассуждения — отдельная интересная ветка, если допускается другой текст ответа. Это оценка исследовательской ценности, не обещание ускорения.

## Отправная точка: что уже измерено

[Каталог MTP](mtp-examples-guide.md) содержит 8409 полных двухтокенных предложений из 11 цепочек по 2048 выходных токенов. Из них 7621 пара — calibration100–109, 788 — heldout110. Все взяты из режима `confidence_collect`, где предложения действительно проверялись.

| Исход | Число пар | Доля |
|---|---:|---:|
| Приняты оба | 6498 | 77.3% |
| Принят только первый | 1111 | 13.2% |
| Не принят первый | 800 | 9.5% |

Первый токен совпал в 7609/8409 = **90.49%** случаев; второй при условии принятого первого — 6498/7609 = **85.40%**. Принято 14107/16818 = **83.88% предложенных токенов**; в знаменателе также есть 800 вторых токенов, отброшенных после первого несовпадения. Это различные метрики. Полные пары не включают укороченные раунды на границе бюджета; поэтому таблица не обязана совпадать с acceptance по всем раундам другого отчёта. Раунды внутри одной цепочки зависимы, 8409 нельзя считать числом независимых задач.

В [heldout timing](mtp-confidence-experiment.md) stock MTP дал 32.44 tok/s против AR 29.83; gate — 24.83. Повышение acceptance само по себе не окупило чтение confidence и управление. Наш обычный DFlash уже проверен: K3/4-bit дал 30.91 против 30.16 tok/s на 5×128, но контрольный baseline менялся; крупного надёжного выигрыша нет. [Сохранённые результаты DFlash](speculative-decoding-research.md).

## Карта направлений

Год ниже — происхождение работы, не дата появления поддержки конкретного checkpoint. Старые полезные идеи помечены явно. «Кандидат» означает, что готовность полного пути для нашего 9B/4-bit на этом Mac не доказана.

| Направление | Что меняется | Статус для этого проекта |
|---|---|---|
| **N-gram / SuffixDecoding / SAM** — идеи 2024, конференции 2025 | Предложения извлекаются из уже доступных токенов, без draft-сети | Первый кандидат: CPU retrieval + наш verifier; training не нужен |
| **Token Recycling** — 2024, ACL 2025 | Альтернативы, уже вычисленные target, сохраняются для будущих предложений | Кандидат; полный метод строит дерево, извлечение logits имеет цену |
| **Multi-candidate / SpecInfer** — 2023–2024 | Target проверяет несколько ветвей вместо одной | Интересно для неоднозначных мест; hybrid state усложняет дерево |
| **DFlash 2** — официальный материал 18.08.2026 | Top-k selector и локальные свёртки согласуют параллельные предложения | Есть готовые другие target; для нашего 9B checkpoint не найден |
| **LibraSpec** — 09.08.2026 | Длина проверки выбирается по ожидаемой выгоде и стоимости | Переносимая идея scheduling поверх работающего DFlash |
| **Quantize the Target, Quantize the Drafter** — 05.07.2026 | Draft адаптирован к квантизованному target; квантизация и окно draft | Полезны отдельные ablations; paper про 4B/NVIDIA, весь training тяжёлый |
| **EAGLE-3** — март 2025, новые интеграции 2026 | Маленький обученный draft использует несколько target features | Exact-target 9B checkpoint есть; verifier и rollback требуют проверки |
| **Domino** — 28.05.2026 | Параллельный backbone + дешёвая причинная коррекция | Архитектурный кандидат, нужны новые обученные веса |
| **DFlare** — 01.06.2026 | Отдельное смешивание target features для каждого draft layer | Архитектурный кандидат; опубликованные Qwen3 не равны Qwen3.5-9B |
| **Lookahead Decoding / Jacobi** — 2024 | Сам target строит и проверяет n-grams параллельными итерациями | Без новой сети, но больше target-вычислений и сложнее cache |
| **SSD / Saguaro** — 03.03.2026 | Следующие drafts вычисляются одновременно с текущей проверкой | В статье отдельное оборудование для draft; один Mac не эквивалентен |
| **Lookahead Reasoning** — 24.06.2025, NeurIPS 2025 | Проверяются смысловые шаги, допускается другой текст | Отдельная ветка качества/latency, без гарантии token parity |
| **MCTS / best-of-N + verifier** | Ищутся лучшие решения среди нескольких траекторий | Оптимизация качества за бюджет времени, не сохранение одного decode |
| **LayerSkip** — 2024 | Ранние слои draft, поздние verifier | Требуется специальное обучение; нельзя просто обрезать наш checkpoint |

Источники и конкретные ограничения перечислены ниже. Серверные speedup из разных papers здесь не ранжируются как результаты одного benchmark.

## 1. Самый дешёвый эксперимент: предложения из повторений

N-gram lookup ищет текущий суффикс в доступном тексте и предлагает уже встречавшееся продолжение. SuffixDecoding использует suffix trees и адаптирует длину предложения; SAM Decoding — suffix automaton для эффективного longest-suffix match. Они особенно интересны для повторяющихся формул, кода, JSON и переноса текста из условия. Это не новые идеи сентября 2026: arXiv v1 обоих suffix-подходов вышли в ноябре 2024. [SuffixDecoding](https://arxiv.org/abs/2411.04975), [SAM Decoding](https://arxiv.org/abs/2411.10666).

В текущем llama.cpp есть `ngram-simple`, `ngram-map-k`, `ngram-map-k4v`, `ngram-mod` и совместное использование нескольких speculators. Это реальная доступная реализация, но переход на GGUF меняет представление target. Для recurrent-моделей merged checkpointing сохраняет/восстанавливает состояние и может повторно выполнять короткий префикс после частичного принятия; его цена существенна. [Документация](https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md), [checkpointing, merged 19.04.2026](https://github.com/ggml-org/llama.cpp/pull/19493).

**Наш эксперимент:** сначала причинный CPU replay уже сохранённых target-генераций. На позиции t retrieval видит только исходный prompt, output[:t] и отдельный фиксированный корпус calibration. Будущие токены текущего ответа используются только как метки. Sweep: длина совпавшего суффикса 2/4/8/16; cap предложения 2/4/8. Измерять coverage, longest accepted prefix, lookup latency. Результат replay — оценка возможности угадывания, не GPU-speedup.

Следующий этап — короткий live benchmark `lookup → target verify`, при отсутствии полезного совпадения AR. Проверка target должна сохраняться; это позволяет ошибочному retrieval не менять greedy output. Вариант `lookup → MTP` тоже полезен, но нужен отдельный baseline, чтобы увидеть добавочную пользу. Нельзя заранее наполнить retrieval настоящим ответом тестовой задачи. При replay calibration нужен leave-one-task-out: из статического корпуса исключаются эта задача, её сохранённый ответ и дубли; разрешённый текущий output[:t] остаётся доступным.

**Почему стоит начать здесь:** почти нет дополнительной памяти весов; можно быстро проверить наличие повторяемости без новой генерации. Риск: математические задачи могут иметь похожие шаблоны, но разные цифры — длинное предложение оборвётся рано.

Родственная идея — Token Recycling: сохранять уже полученные альтернативы и собирать из них будущие предложения. Полная работа использует adjacency structure и tree verification. Для нашего fused-argmax runtime дополнительный top-k readout нельзя считать бесплатным. [Token Recycling](https://arxiv.org/abs/2408.08696).

## 2. Самая интересная обучаемая идея: выбирать из кандидатов

В DFlash 2 сохраняются top-16 на каждой позиции. Небольшой context-gated bilinear selector оценивает соседние пары, затем строится согласованный путь. В авторском Qwen3-4B/GSM8K примере первый target-токен присутствовал в top-1 в 85.4%, в top-16 — 99.5% случаев. Selector отдельно повысил acceptance length 4.27→4.61 при T=0; +2M параметров и +0.6% времени цикла — **авторские измерения**. Дополнительно DFlash2 вводит короткие свёртки внутри draft-блока. [DFlash 2, 18.08.2026](https://inco.ai/blog/dflash2/).

Официально перечисленные готовые DFlash2 checkpoints — Muse-Glimmer-30B и Qwen3.8-27B. Обычный DFlash для нашего Qwen3.5-9B уже есть. Поэтому перенос selector — исследовательский проект; загрузить чужую голову и получить поддержку 9B нельзя. Официальный MLX backend рекомендует `block_size <= 5` для quantized weights из-за стоимости matmul при большей ширине проверки. [Runtime и матрица моделей](https://github.com/z-lab/dflash).

**Наш первый шаг — проверить потолок, ещё до обучения.** На новых calibration-задачах собрать top-1/2/4/8/16 draft logits и настоящий target ID, conditioned на корректном префиксе. Измерить recall@k по позиции и длину префикса, которую получил бы идеальный selector. Отдельно учитывать время top-k. Старые логи p1/p2 содержат только выбранные предложения и не позволяют восстановить альтернативы.

Если target обычно есть в top-4, но редко выбран первым, обучаем маленький reranker на target-generated labels. Если его нет даже в top-16, перестановка кандидатов не решит проблему. Для MTP второй токен вычислен при конкретном первом: при замене первого нужна новая условная ветка, старые logits второго нельзя переносить. Для параллельного DFlash структура иная — именно поэтому DFlash2 здесь особенно интересен.

Близкие новые работы: **Domino** отделяет параллельный backbone от небольшого prefix-conditioned causal head; **DFlare** даёт каждому draft layer собственную обучаемую смесь target features. Обе требуют обучения, не просто изменения sampler. [Domino](https://arxiv.org/abs/2605.29707), [DFlare](https://arxiv.org/abs/2606.02091).

## 3. Несколько цепочек и Monte Carlo: что именно проверяем

### Точное совпадение токенов

Можно сэмплировать несколько коротких кандидатов, объединить общий префикс в дерево и проверить ветви target-моделью. Это семейство SpecInfer / Multi-Candidate Speculative Decoding. При greedy декодировании продолжается ветка, совпадающая с target argmax. Для stochastic decoding требуется корректный multi-candidate sampler: выбор «самой правдоподобной» ветки или большинство голосов не сохраняет распределение. [SpecInfer](https://arxiv.org/abs/2305.09781), [Multi-Candidate Speculative Decoding](https://arxiv.org/abs/2401.06706).

Целую готовую цепочку можно оценить teacher-forcing проходом по её токенам, но в точной speculation принимается только непрерывный префикс до первого отказа. Всё дальше вычислено при уже неверном контексте. Увеличение длины до сотен токенов повышает объём проверки, но не гарантирует столько же полезных токенов.

Пример: после `1/20 = 0` дерево может содержать `.5` и `.0`. Target выберет `.0`; корректную альтернативу можно принять в том же раунде. Это концептуальный пример по нашему отказу, **не утверждение**, что `.0` был в сохранённом top-k: этих logits у нас нет.

Почему нельзя просто добавить произвольный tree-attention mask: Qwen3.5 содержит recurrent Gated DeltaNet state наряду с обычным KV. У разных ветвей должны быть собственные корректные состояния; после выбора ветки нужны rollback/commit. Маска full-attention не управляет состоянием recurrent слоёв. Сначала надёжная реализация через копии состояния и маленький batch ветвей, затем оптимизация совместного префикса. [Архитектура MLX-LM Qwen3.5](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/qwen3_5.py).

Есть экспериментальный **dtree-mlx** с Qwen3.5-9B, но README явно не гарантирует token-by-token equality и приводит результаты на другой машине/конфигурации. Это источник реализации для аудита, а не готовое доказательство корректности наших весов. [Репозиторий](https://github.com/DrHB/dtree-mlx).

**Локальный дизайн:** ширина 1/2/4, глубина 2/4, общий budget узлов 4/8/16. Сначала top-k oracle coverage, затем проверка cache на отказах первой/средней/последней позиции. Основная метрика — полезные tokens/s при одинаковых output IDs; больше acceptance при более медленном verifier не является победой.

### Проверка смысла целого шага

Lookahead Reasoning предлагает draft-шаги и параллельно генерирует target-шаги при предложенных предыдущих шагах, затем semantic verifier сравнивает их. **Параллелизм здесь между шагами; каждый target-шаг сам требует генерации**, это не магический один forward на весь свободный текст. Официальный пример использует Qwen3-32B, draft Qwen3-1.7B и judge Qwen2.5-7B, минимум 4×80GB GPU. На 16GB это не готовый запуск. [Статья, v1 24.06.2025](https://arxiv.org/abs/2506.19830), [код и требования](https://github.com/hao-ai-lab/LookaheadReasoning).

Красивый локальный вариант, **наша адаптация, а не воспроизведение paper**: маленькая модель предлагает преобразования уравнения в ограниченном формате; точная арифметика/SymPy проверяет поддерживаемые операции с явно заданной областью определения. Неподдерживаемое или неоднозначное преобразование возвращается target. Проверить отдельные границы: деление на ноль, потеря корней, неэквивалентные переходы. Метрики — доля решённых задач и время до корректного ответа; исходная последовательность токенов уже не сохраняется. Символьный verifier не проверяет произвольное рассуждение на английском.

### MCTS / best-of-N

MCTS ветвится по действиям/шагам и тратит дополнительные rollouts на выбор решения; process reward или проверка ответа оценивают ветви. Это может улучшить решение за фиксированный бюджет, но не ускоряет автоматически получение той же greedy-цепочки. Пример такой постановки — C-MCTS для математического reasoning. [C-MCTS, 16.02.2025](https://arxiv.org/abs/2502.11169).

Для первого локального опыта проще **best-of-2/4 + точный verifier**, затем сравнить с одним более длинным ответом при одинаковом wall-clock budget. MCTS имеет смысл добавлять, если такое сравнение показывает пользу разнообразия, а verifier способен оценивать промежуточные шаги. Нужны accuracy–latency curves, не только aggregate tok/s нескольких ветвей.

## 4. Улучшить цену draft и verification

**LibraSpec** формулирует длину проверки через marginal gain: стоит ли следующая позиция дополнительного времени verifier. Это особенно уместно для параллельного draft, где длинный блок уже предложен. Готовый MLX/Qwen3.5-9B перенос не подтверждён; оптимальность теоретической модели не равна оптимальности наших kernels. [LibraSpec, 09.08.2026](https://arxiv.org/abs/2608.08721).

Наша практическая цель для действия a:

`estimated useful tokens(a) / (draft + verify + rollback + policy + synchronization time)`.

Для обычной линейной speculation без EOS/budget truncation полезных токенов за цикл в среднем `1 + sum_i P(первые i proposals приняты)`. Не требуется предположение независимости токенов. Размер блока должен окупаться всей ценой цикла. Сначала profile widths 1/2/3/4/5 и несколько длин контекста, затем дешёвая таблица решений; отдельно instrumented и stock runtime. Это собственный план реализации, не готовая оценка speedup.

**Draft-only sliding window** уменьшает контекст дополнительной сети при полном target-контексте. В работе Quantize the Target, Quantize the Drafter это сочетается с квантизацией и обучением draft под quantized target. Исследован Qwen3.5-4B/NVIDIA; весь pipeline также меняет target через QAD. Для нашей цели переносить следует отдельную draft-ablation, а не выдавать новый target за исходный. [Работа, 05.07.2026](https://arxiv.org/abs/2607.04244), [training pipeline](https://github.com/nota-github/adaptfm-quant-dflash).

В локальном `models/qwen3.5-9b-dflash/config.json` окно **4096** у первых пяти draft layers, последний layer использует full attention. Checkpoint обучался со sliding-window attention и длиной последовательности 40k. [Карточка модели](https://huggingface.co/z-lab/Qwen3.5-9B-DFlash).

Локальный sweep: 4096→2048/1024, сохраняя этот рисунок слоёв и не меняя target. Полный attention во всех draft layers — отдельная ablation. Чтобы окно реально влияло, нужен контекст длиннее соответствующего окна; для диагностики можно взять >4k input и короткий output budget. Слишком короткое окно может снизить acceptance; настройка оценивается по полной latency. Дообучение draft под наш 4-bit target — следующий, гораздо более дорогой этап с отдельным train/test.

## 5. Готовые веса и более дорогие альтернативы

**EAGLE3.** Для точного target существует [yuyijiong/Qwen3.5-9B-Eagle3](https://huggingface.co/yuyijiong/Qwen3.5-9B-Eagle3). Это отдельный trained draft на target features; готовые веса экономят обучение. Сам метод старше основного годового окна. [Официальный EAGLE](https://github.com/SafeAILab/EAGLE).

При чтении установленного MLX-VLM обнаружен риск в `_eagle3_verify_target_hot`: argmax сначала ограничен hot vocabulary, полный словарь считается только в найденной позиции коррекции. Настоящий argmax вне hot set на более ранней позиции потенциально может быть пропущен. Это **вывод по коду, не воспроизведённый сбой модели**. Перед сравнением нужен full-vocabulary verifier и проверка всей последовательности. Замечание не относится к уже измеренному native MTP. [Проверенный файл upstream](https://github.com/Blaizzy/mlx-vlm/blob/main/mlx_vlm/speculative/eagle3.py).

Аудит выполнен на установленном **MLX-VLM 0.7.1**, `mlx_vlm/speculative/eagle3.py:295–339`; SHA-256 файла: `def8fc04112ae68b7830aa642ce34123f1bd836235cbf0451d8ce9e9471c5d84`. Ссылка на main выше может меняться.

**Обычный маленький draft.** Кандидаты — [Qwen3.5-0.8B](https://huggingface.co/Qwen/Qwen3.5-0.8B) и [Qwen3.5-2B](https://huggingface.co/Qwen/Qwen3.5-2B); принадлежность к одному семейству не доказывает совпадения tokenizer files. Стандартный MLX-LM speculative path требует возможности обрезать cache; hybrid ArraysCache ограничивает применение к Qwen3.5. Снимать guard без правильного rollback нельзя. Сначала tokenizer/vocab parity и специализированная работа с состоянием, затем подбор размера draft. [generate.py](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/generate.py), [официальный issue1446](https://github.com/ml-explore/mlx-lm/issues/1446).

**Lookahead Decoding** использует Jacobi-итерации и n-grams без дополнительной модели. Он обменивает больше параллельных target-вычислений на меньше последовательных шагов. Это технически интересный порт, но не первая ставка при ограниченном compute и hybrid cache. [Работа 2024](https://arxiv.org/abs/2402.02057).

**SSD/Saguaro** одновременно проверяет текущий draft и готовит продолжения под возможные исходы проверки. Авторы используют отдельное оборудование draft; на одном Mac разделяемые GPU и memory bandwidth могут съесть overlap. CPU retrieval параллельно GPU verifier — более лёгкая локальная гипотеза, но её тоже нужно измерить. [SSD, 03.03.2026](https://arxiv.org/html/2603.03251v1).

**LayerSkip** требует специального training с early-exit objective. Существующий Qwen3.5 checkpoint не приобретает качественный early-exit draft от пропуска слоёв. [LayerSkip](https://arxiv.org/abs/2404.16710).

## Приоритеты и критерии решения

| Порядок | Минимальный эксперимент | Продолжаем, если… | Что нельзя объявлять результатом |
|---|---|---|---|
| 1 | Causal suffix/ngram replay, потом маленький live test | Retrieval часто даёт длиннее 1 токена и окупается | Replay coverage не равен tok/s |
| 2 | DFlash top-k coverage на новых задачах | Есть разрыв recall@1 и recall@4/16 при допустимой цене | Oracle selector не равен обученной модели |
| 3 | Draft window + verify-cost profile | Есть настройка дешевле с полезным acceptance | Низкая draft latency отдельно от verifier |
| 4 | EAGLE3 с full-vocab verification | Все greedy IDs совпадают, total latency меньше | Ограниченный словарь verifier как «точность» |
| 5 | Tiny tree / selector | Добавочные принятые токены окупают ветви | Ширина дерева или acceptance сами по себе |
| 6 | Structured steps + symbolic verifier | Больше корректных решений за тот же budget | Совпадение ответов как token parity |

Для любых новых tuned policies нынешние 11 цепочек уже просмотрены и используются как development material. Calibration/test разделять по **целым задачам**, финальный test — новые непросмотренные строки с проверкой дублей, а не случайные токены старых цепочек. Сравнения на Mac: тот же target/precision, свежий cache, warmup, чередование порядка, полные полезные токены, prefill отдельно, время lookup/draft/verify/rollback, peak memory и контроль сна/питания. Длинная 100×2048 серия остаётся отложенной.

При T=0 проверяем greedy IDs; при sampling равный seed не обещает ту же траекторию, а сохранение распределения требует корректного rejection sampler. Semantic verification и MCTS оцениваются по качеству решения и времени; эти результаты должны жить в отдельной таблице. [Исходный speculative sampling](https://arxiv.org/abs/2302.01318).
